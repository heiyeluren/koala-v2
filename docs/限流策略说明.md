# Koala 限流策略说明

## 一、访问控制（Access Control）

| 类型 | 配置位置 | 说明 |
|------|----------|------|
| **白名单** | `[[access.whitelist]]` | 匹配即放行，优先级最高 |
| **黑名单** | `[[access.blacklist]]` | 匹配即拦截 |

内部使用 `Direct` 算法，不计数，命中即返回结果。

**典型场景**：
- VIP用户直接放行
- 内网IP白名单
- 封禁恶意用户/IP/设备

**配置示例**：
```toml
# 白名单：VIP用户直接放行
[[access.whitelist]]
name = "vip_user_whitelist"
match = { uid = "@whitelist_users" }
result = "vip_allow"

# 白名单：内网IP放行
[[access.whitelist]]
name = "internal_ip_whitelist"
match = { ip = "10.*.*.*" }
result = "internal_allow"

# 黑名单：封禁IP
[[access.blacklist]]
name = "blocked_ip_blacklist"
match = { ip = "@blacklist_ips" }
result = "ip_blocked"

# 黑名单：封禁设备
[[access.blacklist]]
name = "blocked_device"
match = { did = "blocked_device_001" }
result = "device_blocked"
```

## 二、限流算法（Rate Limiting）

| 配置类型 | 内部算法 | 适用场景 |
|----------|----------|----------|
| `count` | Count | 固定时间窗口计数 |
| `freq` | Leak | 滑动窗口/平滑限流 |
| `accumulate` | Base | 累积阈值 + 二级限流 |

### 2.1 `count` - 固定窗口计数

**原理**：
```
时间窗口内累计 N 次后拒绝，窗口结束后重置
```

**工作流程**：
```
┌────────────────────────────────────────┐
│          时间窗口 (如 60s)              │
│                                        │
│  请求1  请求2  请求3  ...  请求N        │
│    ↓      ↓      ↓          ↓          │
│  count=1 count=2 count=3   count=N     │
│                                        │
│  if count >= limit → 拒绝              │
└────────────────────────────────────────┘
        窗口结束时计数器自动过期
```

**配置示例**：
```toml
[[rules.business]]
name = "login_limit"
type = "count"
match = { act = "login", uid = "+" }
limit = { time = "60s", count = 5 }    # 60秒内最多5次
result = "login_limit"
```

**适用场景**：
- 每天最多发帖 10 次
- 每分钟最多登录 5 次
- 每小时最多评论 20 次

**优点**：简单高效，O(1) 复杂度

**缺点**：窗口边界可能出现突发流量（如窗口结束时 count=9，新窗口开始又可以请求 N 次）

---

### 2.2 `freq` - 滑动窗口/漏桶

**原理**：
```
任意连续 N 秒内最多 M 次，无边界突发问题
```

**工作流程**：
```
┌─────────────────────────────────────────────────────┐
│                    时间窗口 (60s)                    │
│                                                     │
│  ←───────────────── 60 秒 ──────────────────→      │
│                                                     │
│  [t1] [t2] [t3] [t4] [t5] ... [t100]               │
│   ↑                            ↑                    │
│  最旧                         最新                   │
│                                                     │
│  检查: 窗口内的请求数 >= limit.Count ?              │
│  如果是 → 拒绝                                      │
└─────────────────────────────────────────────────────┘
```

**配置示例**：
```toml
[[rules.advanced]]
name = "api_smooth_limit"
type = "freq"
match = { act = "api_call", uid = "+" }
limit = { time = "60s", count = 100 }   # 任意60秒内最多100次
result = "api_limit"
```

**适用场景**：
- API 调用平滑限流
- 搜索请求限制
- 需要精确控制流量的场景

**优点**：平滑限流，无边界突发问题

**缺点**：存储开销较大（需要记录每次请求的时间戳）

---

### 2.3 `accumulate` - 累积阈值 + 二级限流

**原理**：
```
总量达到阈值前无限制，达到后启用二级限流
```

**工作流程**：
```
┌─────────────────────────────────────────────────────────────┐
│  主计数器 (累计总量，无TTL)                                   │
│                                                             │
│  请求1...请求20 (base=20)                                   │
│        ↓                                                    │
│  达到基础阈值，启用次级限制                                   │
│        ↓                                                    │
│  ┌─────────────────────────────────────┐                   │
│  │  次级计数器 (时间窗口内)              │                   │
│  │  每 10 秒最多 1 次                   │                   │
│  │  count >= 1 → 拒绝                  │                   │
│  └─────────────────────────────────────┘                   │
└─────────────────────────────────────────────────────────────┘
```

**配置示例**：
```toml
[[rules.advanced]]
name = "ask_base_control"
type = "accumulate"
match = { act = "ask", ip = "+" }
limit = { base = 20, time = "10s", count = 1 }  # 总量超过20后，每10秒限1次
result = "deny"
```

**适用场景**：
- 正常用户快速操作，高频用户受限
- "每天超过 20 次后，每 10 秒限 1 次"
- 渐进式限流

**优点**：对正常用户友好，只限制高频用户

**缺点**：主计数器不会自动过期，需要外部管理或设置合理的清理策略

## 三、规则优先级

规则按以下顺序执行，先匹配先返回：

```
白名单 > 黑名单 > Business > Post > Advanced > Default
```

**执行流程**：
```
请求进入
    │
    ▼
┌─────────────┐
│  白名单检查  │ ──匹配──▶ 直接放行
└─────────────┘
    │不匹配
    ▼
┌─────────────┐
│  黑名单检查  │ ──匹配──▶ 直接拦截
└─────────────┘
    │不匹配
    ▼
┌─────────────┐
│  业务规则   │ ──超限──▶ 返回限流
└─────────────┘
    │未超限
    ▼
┌─────────────┐
│  发帖规则   │ ──超限──▶ 返回限流
└─────────────┘
    │未超限
    ▼
┌─────────────┐
│  高级规则   │ ──超限──▶ 返回限流
└─────────────┘
    │未超限
    ▼
┌─────────────┐
│  默认规则   │ ──超限──▶ 返回限流
└─────────────┘
    │未超限
    ▼
  允许通过
```

## 四、匹配模式

| 语法 | 示例 | 说明 |
|------|------|------|
| 精确匹配 | `"login"` | 值等于 "login" |
| 任意非空 | `"+"` | 匹配任何非空值 |
| 取反 | `"!admin"` | 值不等于 "admin" |
| 多值 | `"post,comment"` | 值为其中之一 |
| 范围 | `"1-100"` | 数值在范围内 |
| 大于 | `">1000"` | 数值大于阈值 |
| 小于 | `"<100"` | 数值小于阈值 |
| IP通配 | `"192.168.*.*"` | IP匹配通配符 |
| 字典引用 | `"@whitelist"` | 值在字典文件中 |

**匹配示例**：
```toml
# 精确匹配
match = { act = "login" }

# 任意用户
match = { act = "post", uid = "+" }

# 非管理员用户
match = { act = "admin", uid = "!admin" }

# 多种行为
match = { act = "post,comment,reply" }

# 等级在1-10之间
match = { act = "vip_action", level = "1-10" }

# 字典引用
match = { uid = "@vip_users" }

# IP通配符
match = { ip = "192.168.*.*" }
```

## 五、算法选择指南

| 需求 | 推荐算法 | 配置类型 | 理由 |
|------|----------|----------|------|
| 每天/每小时固定次数限制 | Count | `count` | 简单高效 |
| API 限流、需要平滑控制 | Leak | `freq` | 无边界突发问题 |
| 正常用户不限、高频用户限速 | Base | `accumulate` | 渐进式限流 |
| 黑白名单 | Direct | 访问控制规则 | 无需计数 |

## 六、完整配置示例

```toml
# =============================================================================
# 元数据
# =============================================================================
[meta]
version = "1.0.0"
description = "限流策略配置"

# =============================================================================
# 字典文件
# =============================================================================
[dicts]
whitelist_users = "conf/whitelist_users.txt"
blacklist_ips = "conf/blacklist_ips.txt"

# =============================================================================
# 结果模板
# =============================================================================
[results]
[results.allow]
code = 0
message = "ok"
auth_type = 0

[results.vip_allow]
code = 0
message = "VIP用户放行"
auth_type = 0

[results.login_limit]
code = 4001
message = "登录过于频繁，请稍后重试"
auth_type = 1    # 需要验证码

[results.api_limit]
code = 4201
message = "API调用频率超限"
auth_type = 0

# =============================================================================
# 访问控制规则
# =============================================================================
[access]

# VIP用户白名单
[[access.whitelist]]
name = "vip_user_whitelist"
match = { uid = "@whitelist_users" }
result = "vip_allow"

# IP黑名单
[[access.blacklist]]
name = "blocked_ip_blacklist"
match = { ip = "@blacklist_ips" }
result = "ip_blocked"

# =============================================================================
# 限流规则
# =============================================================================
[rules]

# 登录限流（固定窗口）
[[rules.business]]
name = "login_rate_limit"
type = "count"
match = { act = "login", uid = "+" }
limit = { time = "60s", count = 5 }
result = "login_limit"

# API限流（滑动窗口）
[[rules.advanced]]
name = "api_smooth_limit"
type = "freq"
match = { act = "api_call", uid = "+" }
limit = { time = "60s", count = 100 }
result = "api_limit"

# 高频用户限流（累积阈值）
[[rules.advanced]]
name = "ask_base_control"
type = "accumulate"
match = { act = "ask", ip = "+" }
limit = { base = 20, time = "10s", count = 1 }
result = "api_limit"

# 默认全局限流
[[rules.default]]
name = "global_default_limit"
type = "count"
match = { act = "+", uid = "+" }
limit = { time = "60s", count = 100 }
result = "api_limit"
```

## 七、auth_type 验证类型说明

| 值 | 说明 |
|----|------|
| 0 | 无需额外验证 |
| 1 | 需要图形验证码 |
| 2 | 需要短信验证码 |

当限流触发时，客户端可根据 `auth_type` 决定是否弹出验证码等二次验证。
