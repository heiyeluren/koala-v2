## 2. 技术设计与代码一致性

### 2.1 🔴 严重问题

#### 问题 2.1.1: 算法类型名称不一致

| 来源 | 算法类型 |
|------|----------|
| 技术设计文档 | `direct`, `count`, `base`, `leak` |
| 实际代码 | `count`, `freq`, `accumulate` |
| 用户手册 | `count`, `freq` |

**代码位置**: `internal/config/rules.go:14-18`
```go
const (
    RuleTypeCount      = "count"
    RuleTypeFreq       = "freq"
    RuleTypeAccumulate = "accumulate"
)
```

**影响**: 技术设计文档中的算法类型名称与代码完全不匹配，会误导开发人员。

**修复建议**: 更新技术设计文档 `docs/v2-tech-design/05-CONFIG-REFERENCE.md`，将算法类型改为实际支持的 `count`、`freq`、`accumulate`。

---

#### 问题 2.1.2: 存储类型 redis_cluster 未实现 ✅ 已修复

| 文档描述 | 修复后 |
|----------|--------|
| ~~`local`, `redis`, `redis_cluster`~~ | `local`, `redis` |

**修复方案**: 移除文档中 `redis_cluster` 类型的描述，当前仅支持单机 Redis。

---

### 2.2 🟠 重要问题

#### 问题 2.2.1: 存储降级行为未明确

技术设计文档承诺了 Redis 故障时自动降级到本地存储，但未说明：
- 数据一致性如何保证？
- Redis 恢复后数据如何同步？
- 是否支持双写？

**修复建议**: 补充降级策略文档，明确数据一致性处理方式。

---

#### 问题 2.2.2: TOCTOU 竞态条件未处理

Browse → 允许 → Update 流程存在时间窗口竞态：
```
请求A: Browse(count=4) → 允许 → Update
请求B: Browse(count=4) → 允许 → Update
结果: count 从 4 变成 6，两个请求都认为自己是第5个
```

**影响**: 在高并发下可能超出限流阈值。

**修复建议**:
- 文档中说明这是预期行为（最终一致性）
- 或实现原子性的 Browse+Update 操作
